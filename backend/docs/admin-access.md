# Создание владельца и администраторов

## Первый запуск

1. Сгенерируйте отдельный ключ командой `openssl rand -hex 32`. Сохраните его
   в серверной переменной `ADMIN_SETUP_KEY`. Для Compose задайте её в корневом
   `.env`: значение уже передаётся бэкенду из обоих compose-файлов. Не используйте
   `JWT_SECRET`, не помещайте ключ в `VITE_*` или репозиторий.
2. Запустите обновлённый бэкенд. Миграция `011_admin_setup.sql` применяется
   автоматически при `MIGRATE_ON_START=true`.
3. Откройте `/setup` на фронтенде. Введите ключ, имя, фамилию, почту и пароль.
   В production используйте HTTPS. Пароль: минимум 8 символов, максимум 72 байта UTF-8.
4. Войдите через `/authorization`. Аккаунт имеет `is_admin=true` и
   `can_manage_admins=true` — право владельца управлять администраторами.
5. Удалите `ADMIN_SETUP_KEY` из серверной конфигурации и перезапустите API.
   Это дополнительное удаление секрета: настройка уже закрыта постоянной записью БД.

Пустой ключ отключает настройку. Одновременные запросы сериализуются блокировкой
единственной строки `admin_setup`: успешно выполнится только один. Удаление или
блокировка аккаунтов, смена ключа и рестарт API не открывают настройку снова.
Ключ и пароли передаются в JSON, не возвращаются в ответах и не логируются.

## Приглашение администратора

Владелец открывает `/admin/administrators`, выбирает «Пригласить нового», указывает
имя, фамилию, почту и подтверждает действие своим текущим паролем.
Нужен настроенный SMTP: `SMTP_HOST`, `SMTP_PORT` (обычно 587), `SMTP_USER`,
`SMTP_PASSWORD`, `SMTP_FROM`. SMTP-сервер должен поддерживать STARTTLS с валидным
сертификатом: незашифрованная отправка запрещена. `APP_URL` должен содержать публичный адрес фронтенда.
Письмо отправляется фоновой очередью, поэтому успех запроса означает постановку
в очередь, а не подтверждение доставки. Ошибки доставки видны в `mail_outbox`.

Новый аккаунт до активации не имеет прав администратора и не может войти.
Письмо содержит одноразовую ссылку `/activation#token=…` со сроком 24 часа.
Токен во фрагменте не передаётся веб-серверу; страница убирает его из адресной строки.
Получатель задаёт пароль: сервер атомарно назначает `is_admin=true`, сохраняет хеш
пароля и погашает приглашение. Затем пользователь входит обычным способом.
В таблице приглашений хранится SHA-256 токена, исходная ссылка находится только
в ожидающем отправки письме и стирается из очереди после доставки.
Содержимое писем не выводится в лог даже при отключении SMTP.

Кнопка «Отправить повторно» заполняет форму. После подтверждения паролем владельца
создаётся новая ссылка, предыдущая отзывается. Повторная отправка не меняет имя
существующего аккаунта. При ошибке SMTP настройте почту и отправьте приглашение заново.

## Назначение существующего пользователя

В том же разделе выберите «Назначить существующего», введите почту и свой текущий
пароль. Пользователь должен быть активен и уже иметь пароль. Сервер сохраняет
учебные профили, добавляет `is_admin=true` и отзывает его старые сессии.
Для доступа к панели пользователь входит заново. Приглашения и назначения
не выдают `can_manage_admins`: управление администраторами остаётся у владельца.

Право владельца проверяется непосредственно в БД при каждом запросе управления.
Изменения прав и запись в `admin_access_audit` выполняются одной транзакцией.
В аудите сохраняются действие, инициатор, получатель, его почта и время; секретов нет.
Другие администраторы не могут редактировать или блокировать владельца.

## Существующая установка

Миграция закрывает первоначальную настройку, если в базе уже есть администраторы.
Владельцем становится администратор с минимальным ID среди активных; если активных
нет — с минимальным ID среди остальных. Для появления нового пункта меню нужно
заново войти или обновить сессию. Настройка по ключу не даёт захватить такую установку.

CLI `createadmin` остаётся резервным серверным инструментом. На пустой установке
он создаёт владельца и закрывает настройку; на настроенной — обычного администратора.

## API

Все пути относительно `/api/v1`; JSON-ответы имеют обёртку `data`.

| Метод | Путь | Доступ | Результат |
| --- | --- | --- | --- |
| GET | `/auth/setup` | публичный | `{data: {available: boolean}}` |
| POST | `/auth/setup` | серверный ключ в `setup_key` | 201 `{data: {created: true}}` |
| GET | `/admin/administrators` | Bearer владельца | 200 `{data: Administrator[]}` |
| POST | `/admin/administrators/invitations` | Bearer + `current_password` владельца | 204 |
| POST | `/admin/administrators/promote` | Bearer + `current_password` владельца | 204 |
| POST | `/auth/activate` | одноразовый `token` + новый `password` | 204 |

Тела запросов и ошибки также описаны на странице фронтенда `/api-docs`.
Подбор ключа ограничен адресом реального TCP-соединения (заголовки клиента
не позволяют обойти лимит), подтверждение пароля — ID авторизованного пользователя.
Лимит — 5 запросов за 15 минут на ключ; счётчики живут в процессе API.
